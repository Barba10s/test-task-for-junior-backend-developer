# Task Service

Сервис для управления задачами с HTTP API на Go.

## Требования

- Go `1.23+`
- Docker и Docker Compose

## Быстрый запуск через Docker Compose

```bash
docker compose up --build
```

После запуска сервис будет доступен по адресу `http://localhost:8080`.

Если `postgres` уже запускался ранее со старой схемой, пересоздай volume:

```bash
docker compose down -v
docker compose up --build
```

Причина в том, что SQL-файл из `migrations/0001_create_tasks.up.sql` монтируется в `docker-entrypoint-initdb.d` и применяется только при инициализации пустого data volume.

## Swagger

Swagger UI:

```text
http://localhost:8080/swagger/
```

OpenAPI JSON:

```text
http://localhost:8080/swagger/openapi.json
```

## API

Базовый префикс API:

```text
/api/v1
```

Основные маршруты:

- `POST /api/v1/tasks`
- `GET /api/v1/tasks`
- `GET /api/v1/tasks/{id}`
- `PUT /api/v1/tasks/{id}`
- `DELETE /api/v1/tasks/{id}`

## Комментарии к заданию

### Принятые предположения и решения

#### 1. Время суток (time_of_day)
**Проблема:** В скриншоте интерфейса есть выбор времени, но в текстовом описании требования упоминаются только даты.

**Решение:** Добавлено опциональное поле `time_of_day` (формат HH:MM).

**Обоснование:**
- Поле опционально — не ломает существующий API
- Архитектура стратегий позволяет добавить без изменений существующего кода

#### 2. Проверка конфликтов времени
**Проблема:** Пользователь может создать две задачи на одно время (например, 09:00), что приведёт к двойному выполнению.

**Решение:** При создании задачи с `time_of_day` проверяется наличие других задач на то же время. Возвращается `409 Conflict`.

**Обоснование:**
- Защита от случайного дублирования
- Семантически корректный HTTP-статус (409, а не 400)

**Ограничение:** Проверяется только точное совпадение времени, без учёта типа периодичности. Например, «каждый понедельник 09:00» и «15 число 09:00» (если 15-е — понедельник) не считаются конфликтом. Полная проверка требует генерации дат наперёд.

#### 3. Валидация времени
**Проблема:** Пользователь может ввести некорректное время (`9:00`, `25:00`, `12:60`).

**Решение:** Валидация через регулярное выражение `^([01]\d|2[0-3]):([0-5]\d)$`.

**Обоснование:**
- Строгий формат HH:MM (ведущий ноль обязателен)
- Диапазон: часы 00–23, минуты 00–59
- Одно сообщение об ошибке для формата и значения

#### 4. Дубликаты дат в specific
**Проблема:** Пользователь может отправить `[1, 15, 15]` — дата 15 дублируется.

**Решение:** Проверка на дубликаты в `SpecificStrategy.Validate()`. Возвращается `400 Bad Request`.

**Обоснование:** Защита от злоупотреблений и логических ошибок.

#### 5. Лимит на количество дат
**Проблема:** Пользователь может отправить 1000 дат в массиве.

**Решение:** Максимум 31 дата в `specific`.

**Обоснование:** Защита от DoS-атак и чрезмерного использования ресурсов.

#### 6. Часовые пояса
**Проблема:** В задании не указано, в каком часовом поясе хранить даты.

**Решение:** Все даты в **UTC**.

**Обоснование:** Стандарт для backend-систем. Конвертация в локальный пояс — задача фронтенда или сервиса уведомлений.

#### 7. Короткие месяцы (февраль)
**Проблема:** Задача настроена на 30-е число, но в феврале 28 (или 29) дней.

**Решение:** API хранит расписание, но не определяет поведение для отсутствующих дат. Обработка делегирована планировщику задач.

**Обоснование:** 
- Разделение ответственности: API отвечает за хранение и валидацию, планировщик — за исполнение.
- Гибкость: планировщик может применять разные стратегии (пропуск, перенос, уведомление).
- Бизнес-логика: выбор стратегии требует уточнения.

Выбор стратегии зависит от бизнес-требований и требует уточнения.

#### 8. Пересекающиеся расписания
**Проблема:** Пользователь может создать «каждый день» + «15 число» — в 15-й день будет двойное выполнение.

**Решение:** Не блокируется.

**Обоснование:** Это может быть осознанным решением пользователя (например, «ежедневно + дополнительно в зарплатные дни»). 

### Граничные случаи, которые учтены

| Случай | Как обработан |
| Пустой массив дат | `400 Bad Request: dates array cannot be empty` |
| Дубликаты дат | `400 Bad Request: duplicate date: 15` |
| Дата > 31 | `400 Bad Request: each date must be between 1 and 31` |
| Слишком много дат (>31) | `400 Bad Request: maximum 31 dates allowed` |
| `interval_days: 0` | `400 Bad Request: interval_days must be >= 1` |
| Неверный parity | `400 Bad Request: parity must be 'even' or 'odd'` |
| Время `9:00` (без ведущего нуля) | `400 Bad Request: must be in HH:MM format` |
| Время `25:00` (несуществующее) | `400 Bad Request: must be 00-23:00-59` |
| Конфликт времени | `409 Conflict: task with time 09:00 already exists` |
| Обновление своей задачи (то же время) | `200 OK` (не считается конфликтом) |
| Задача не найдена | `404 Not Found` |

### Архитектурные решения

#### Pattern: Strategy
Каждый тип периодичности — отдельная стратегия (`DailyStrategy`, `MonthlyStrategy`, etc.). Все реализуют интерфейс `FrequencyStrategy`:
- `IsValid(date) bool`
- `NextOccurrence(from) time.Time`
- `Description() string`

**Преимущество:** Новый тип добавляется без изменения существующих стратегий (Open/Closed Principle).

#### Хранение в БД: JSONB
Поле `frequency` типа `JSONB` в PostgreSQL.

**Преимущества:**
- Гибкость схемы (не нужно миграций для новых полей)
- Возможность индексации по ключам
- Структура 1:1 с доменной моделью

#### Валидация на уровне домена
Все проверки в `Frequency.Validate()` и стратегиях.

**Преимущество:** Валидация не зависит от транспорта (HTTP, gRPC, CLI).

### Принятые ограничения

1. **Weekly (еженедельно)**: Не реализовано. Архитектура позволяет добавить без изменений существующего кода.
2. **Дата начала/окончания**: Задачи повторяются бесконечно с даты создания.
3. **Предпросмотр расписания**: API не возвращает список ближайших дат выполнения. Метод `NextOccurrence()` реализован в домене, можно добавить эндпоинт `GET /tasks/{id}/next-occurrences`.
4. **Полная проверка конфликтов**: Проверяется только точное совпадение `time_of_day`, без учёта типа периодичности.
5. **Дни месяца для monthly**: Поддерживаются дни с 1 по 30. День 31 не поддерживается, так как отсутствует в 7 месяцах года (согласно требованиям задания).
6. **Короткие месяцы (февраль)**: Если задача настроена на дату, отсутствующую в месяце (29–30 в феврале), обработка делегирована планировщику задач.


### Как добавить новый тип периодичности

1. Добавить константу в `FrequencyType`
2. Создать стратегию (например, `WeeklyStrategy`) с реализацией интерфейса `FrequencyStrategy`
3. Обновить `ToStrategy()` в `Frequency`
4. Добавить валидацию в `Validate()`
5. Добавить описание в `Description()`
